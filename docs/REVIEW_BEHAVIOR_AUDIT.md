확정 계약은 [데이터](architecture/DATA_MODEL.md), [사용자 흐름](architecture/USER_FLOW.md), [API](architecture/API_CONTRACT.md), [화면](architecture/SCREEN_SPEC.md) 원본에 반영했다. 원격 문서 통합 커밋 `d750dd2`를 fast-forward 반영하고 새 문서 경로에 기존 정책과 이번 확정 설계를 모두 보존했다.

삭제 정합성 → 세트 복습 필터 → 완료 안내와 대표 화면 검증 순서로 구현했다. 하위 데이터 정리에는 기존 서비스 흐름을 연결했으며 새 삭제 프레임워크나 DB 스키마를 추가하지 않았다. 카드·세트·섹션 삭제 API에는 소유 관계 확인을 위한 필수 `userId` 쿼리를 추가했고 기존 카드 삭제 화면과 API 클라이언트도 수정했다.

## 변경 전 삭제 경로의 차이 (초기 점검 이력)

엔티티는 부모를 객체 관계 대신 ID 필드로 보관한다. 검토한 엔티티에는 JPA cascade 관계가 없다. 아래는 서비스 및 저장소 코드 기준이며 실제 삭제 API의 E2E 실행 결과는 아니다.

| 삭제 대상 | 삭제 처리 | 남는 데이터 및 조회 영향 |
| --- | --- | --- |
| 카드 | `FlashCardService.deleteFlashCard`: 기록 삭제 후 카드 삭제 | 기존 테스트도 이 삭제 순서를 요구 |
| 학습 세트 | `MaterialService.deleteMaterial`: 카드 삭제 후 세트 삭제 | 복습 기록을 명시적으로 삭제하지 않음. 카드와 JOIN하는 기록 화면에서 해당 기록이 제외될 수 있음 |
| 기본 섹션 | `CategoryService.deleteCategory`: 섹션만 삭제 | 세트·카드·기록의 부모 연결이 끊어질 수 있음 |
| 폴더 | `DeckService.deleteDeck`: 폴더만 삭제 | 하위 데이터가 남고 폴더까지 JOIN하는 복습 대상·기록 조회에서 제외될 수 있음 |

설계의 'ReviewHistory는 삭제보다 보존을 우선'은 삭제 대상별 처리와 삭제 후 조회 방법까지 정의하지 않는다. 단순히 기록 행만 남기는 것으로는 사용자가 이력을 볼 수 있다는 보장이 없다.

## 검토했던 선택지 (추천안 승인 완료)

### 1. 삭제 정책

- **MVP1 추천: 명시적 영구 삭제를 선택하면 하위 데이터와 해당 복습 기록도 일관되게 삭제.** 현재 카드 삭제와 일치하고 보존용 스키마 없이 완결 가능하다. 학습 이력 복구·장기 통계는 불가능하므로 확인 문구와 설계의 보존 예외를 명확히 해야 한다. 복습 알고리즘 변경을 이유로 기존 기록을 삭제하는 것은 허용하지 않는다.
- 대안: 보관/소프트 삭제로 기록 유지. 장기 기억 분석에 유리하지만 부모·카드 보관, 복습 대상 제외, 기록 조회, 복구와 영구 삭제를 함께 설계해야 한다. DB 계약 변경이 필요하다.
- 임시 대안: 하위 데이터나 기록이 있으면 삭제 거부. 데이터 손실은 막지만 사용자의 정리 흐름을 제한한다.

### 2. 학습 세트에서 시작하는 복습

- **추천: 선택한 세트의 기한 카드만 복습.** 전체 오늘의 복습과 같은 일정 정책을 유지하며 범위만 좁힌다. 추가 API 필터와 소유 관계 검증이 필요하다.
- 대안: 세트의 모든 카드 연습. 기한 전 재학습이 정규 복습 일정·기록에 영향을 주는지 별도 정의가 필요하다.
- 검증: 두 세트에 각각 기한 카드가 있을 때 선택한 세트만 노출되고 다른 사용자 세트에 접근하지 못해야 한다.

### 3. AGAIN과 완료

- **MVP1 추천: 현재처럼 목록을 한 번 처리하고 '이번 복습을 마쳤습니다'로 안내.** AGAIN은 10분 뒤 새 조회에서 대상이 된다. 대기 없이 종료할 수 있고 별도 세션 저장 구조가 필요 없다. 다음 복습이 남을 수 있음을 안내한다.
- 대안: 같은 세션에 기한이 된 AGAIN 카드를 다시 투입. 재조회·대기·진행률·종료 기준과 세트 필터 유지까지 설계해야 한다.
- 검증: 마지막 카드가 AGAIN이어도 저장은 성공하며, 문구가 하루 전체 복습 완료를 보장하지 않아야 한다.

## 이번에 추가한 검증

- `ReviewServiceTest`: 네 결과별 일정과 저장 내용, 월 경계, 시간 생략, 요청/결과 누락, 소유 카드 조회 실패, 저장 예외 전달.
- `ReviewTransactionTest`: 테스트용 임베디드 H2에서 기록과 변경 일정을 flush한 뒤 예외를 발생시키고, 트랜잭션 종료 후 기록 수와 원래 일정이 복구되는지 검사. 운영 파일 DB는 사용하지 않는다.
- 소유 조회 실패 단위 테스트는 실제 소유 관계 JOIN 쿼리나 로그인 인증 검증을 대체하지 않는다.
- 실행 결과는 Maven Surefire 보고서로 확인한다. 후속 UI E2E 결과는 위 구현 후 검증 결과에 기록했다. 운영 PostgreSQL은 검증하지 않았다.

## 최소 하네스 파일럿

초기 기능 구현 이후 전용 `passmate-review` Skill 한 개와 CI를 추가했다. 기존 설계/구현/디버깅 Skill에 필요한 검토만 보태며 별도 상시 오케스트레이터 실행기는 추가하지 않았다. [현재 운영과 파일럿 결과](AI_WORKFLOW.md)를 따른다.

1. 작업 시작: 적용 정책, 변경 범위와 현재 작업 완료 조건.
2. 구현 검증: 관련 서비스 테스트와 대표 화면 흐름. 실패 시 수정 후 해당 검증 재실행.
3. 독립 검토가 필요한 경우: 구현자의 결론 대신 요구사항·diff·테스트 증거를 기준으로 확인.
4. 문서: 변경된 계약의 원본만 갱신. 원격 통합 문서 반영 전에는 구형·신형 문서에 정책을 중복 확정하지 않는다.
5. 에이전트 평가: 기록 저장 누락을 발견하는 사례, 정책 변경을 임의 확정하지 않는 사례, 작은 수정에 불필요한 승인·전수 검사를 요구하지 않는 반대 사례를 비교. 제품 테스트 통과와 에이전트 행동 평가 통과를 구분한다.

정책 승인과 구현, UI E2E 및 독립 코드 검토는 완료했다. 합성 행동 관찰은 수행했지만 사람의 최종 행동 평가나 Skill 변경 전후의 성능 비교를 수행한 것은 아니다. 커밋·push·병합도 수행하지 않았다.
