# PassMate 문서 정리 제안 및 점검 결과

> 상태: 제안안. 기존 step1~step5 문서는 아직 이동·삭제하지 않는다.

## 문제 진단

- MVP 범위, 사용자 용어, Category 숨김 정책이 AGENTS.md, ARCHITECTURE.md, FRONTEND.md, 각 step 문서에 반복된다.
- 단계 번호(step1~step5)는 작성 순서를 설명하지만, 유지보수 시 어떤 파일이 정책의 원본인지 드러내지 않는다.
- 설계 화면 경로는 `/folder/` 중심이지만 실제 코드 트리에는 `/deck/[deckId]/category/[categoryId]/...` 경로도 남아 있어, 현재 사용 경로와 레거시 경로를 확인해야 한다.
- 사용자 시나리오의 복습 결과 저장은 정의되어 있으나, 기본 복습 간격 및 결과별 갱신 정책은 상세 설계에 명확하지 않다.
- API 문서에는 학습 방식별 대시보드 큐 확장 계약이 있지만, 복습 결과의 의미를 공통 엔진에 연결하는 계약은 별도 검토가 필요하다.

## 문서 책임의 단일 원본(SSOT)

| 원본 | 단독 책임 |
| --- | --- |
| `docs/PRODUCT_VISION.md` | 왜 만드는지, 장기 기억 유지, 신규 기능 판단 기준 |
| `ARCHITECTURE.md` | 현재 MVP 범위, 도메인 관계, 변경 금지 원칙 |
| `docs/architecture/USER_FLOW.md` (제안) | 사용자가 수행하는 전체 학습·복습 흐름 및 완료 기준 |
| `docs/architecture/DATA_MODEL.md` (제안) | ERD, 엔티티, 복습 상태·이력 |
| `docs/architecture/API_CONTRACT.md` (제안) | 엔드포인트와 응답 계약 |
| `docs/architecture/SCREEN_SPEC.md` (제안) | 화면별 책임, 라우트, 주요 상호작용 |
| `SPRING.md`, `FRONTEND.md`, `API_STYLE.md`, `GIT.md` | 기술 구현 규칙만 |
| `AGENTS.md` | 읽을 문서 라우팅, 검증 및 안전 규칙만 |

기존 step2 정보 구조는 별도 파일로 유지하기보다 USER_FLOW의 메뉴/내비게이션 절에 합치는 것을 권장한다.

## 안전한 마이그레이션 순서

1. 코드 기준으로 현재 라우트/API/엔티티와 설계 차이를 확인해 '현재 동작', '목표 설계', '미구현'으로 표시한다.
2. 새 이름의 문서 네 개를 생성하고 중복 정책을 원본 문서 링크로 치환한다.
3. AGENTS.md, README.md 및 다른 문서의 참조 경로를 일괄 변경한다.
4. 기존 step 문서는 링크가 깨지지 않도록 짧은 이동 안내 문서로 일시 유지한다.
5. 코드 변경 없이 문서 링크와 범위 일치 여부를 검증한 후, 별도 승인 시 레거시 문서를 정리한다.

## 문서 갱신 규칙 제안

- 코드 작업 전 해당 기능의 원본 설계 문서를 확인한다.
- API/데이터/화면 동작이 달라지면 같은 작업 단위에서 해당 원본 문서를 갱신한다.
- 제품 비전이나 MVP 범위 변경은 사용자 승인 없이 수행하지 않는다.
- 문서가 코드와 다르면 조용히 덮어쓰지 말고 차이를 보고한다.
- 작업 완료 보고에는 '관련 문서 갱신 여부'를 포함한다.
- 동일 정책 문구를 여러 문서에 복사하지 않고 링크한다.

## 이번 브랜치에서 적용한 범위

- 제품 비전 신설
- AGENTS.md와 ARCHITECTURE.md에 제품 비전 연결
- 문서 구조 정리 계획 기록

기존 설계 문서 통합, 삭제, 코드 및 복습 알고리즘 변경은 수행하지 않았다.
